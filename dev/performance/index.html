Performance

All timings are wall times, best of 3, with threads pinned to cores (JULIA_EXCLUSIVE=1, OMP_PROC_BIND=close). Logs are in benchmark/results/.

Free space against Fortran

bdmk against bdmk_fortran on the same tree (Laplace kernel; Fortran built with -O3 -march=native, OpenBLAS and OpenMP). The density is $f = -\Delta u/(4\pi)$ for a sum of three Gaussians in a box of size 1.18, so the exact potential $u$ is known. Both codes reach the same error against $u$ and agree with each other to about $10^{-13}$ (benchmark/native_vs_fortran.jl).

Periodic against C++

Against the C++ periodic solver (PeriodicDMK bench_steps <cell> multi): four Gaussians down to width 0.007, norder = 16, one socket of a genoa node, each case on its own node (benchmark/periodic_cases.disbatch, logs in benchmark/results/periodic/cases/). Both codes evaluate the same density point by point, apply the same work-saving rules and exact wide transforms, and build the same forest.

The Julia time is split into the sampling stage, the adaptive refinement that evaluates the density (its cost depends on how $f$ is implemented), and the rest, which does not depend on $f$ (see Sampling the density once). The columns are:

  • f everywhere: sample_once = false, the C++ rules (the potentials agree with C++ to $2\cdot10^{-13}$ at eps = 1e-9);
  • sampling + rest: the default sample_once = true (agreement with C++ to about eps: $8\cdot10^{-11}$ at eps = 1e-9);
  • SIMD density: the same with the SIMD.jl batch density of benchmark/periodic_vs_cpp.jl (DENSITY=simd), for which the C++ code has no counterpart.

Where the rest goes (hexagonal cell, eps = 1e-9): at one thread, the GEMM-bound stages dominate: plane waves 0.92 s, near field 0.87 s, upward pass 0.38 s. Their kernels run at the FP64 peak. At 48 threads the plane waves (≈ 75 ms) are bound by memory bandwidth: the expansions of a level are hundreds of MB.
